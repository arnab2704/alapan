# Alapon V0.1 Foundation — Architecture

Status: implemented. Scope: website shell, Bengali/English i18n, design
system, homepage, Play, ShobdoShakti, Bengali calendar and festival
calendar, daily quiz, Discover/Theke Adda placeholders, database foundation, Bengali
engine, game engine, automated tests.

Explicitly out of scope for this pass (see `ALAPON_FIRST_DRAFT.md` for the
full long-term vision): business directory, creator marketplace, payments,
full social network, unrestricted Theke Adda, native mobile apps, complex
AI, advertising. The structure below leaves room for these without requiring
a rewrite.

## 2. Why a modular monolith, still

Next.js App Router serves the whole site. `packages/bengali` and
`packages/game-engine` are framework-free (no React, no Next, no DB) so they
stay unit-testable in isolation and reusable if a NestJS service is ever
split out later, per the original decision log.

## 3. Bengali tokenization strategy

Two deliberately separate layers - conflating them is the most common bug
in Bengali-aware software:

- **`graphemes(text)`** (`packages/bengali/src/graphemes.ts`): Unicode
  extended grapheme clusters via `Intl.Segmenter`, with a manual fallback.
  This is "how many visible characters" for cursor movement, truncation,
  and general text editing. A vowel sign must never be separated from its
  base consonant here.
- **`tokenizeBengali(text)`** (`packages/bengali/src/tokenize.ts`):
  akshara-level _game tokens_. Consonant clusters joined by `্` (virama) -
  conjuncts like ক্ষ, ন্ত্র, দ্যা - are merged into one unit, with any
  trailing vowel sign/modifier attached. This is deliberately independent
  of ICU grapheme-cluster behavior (which varies by version for Indic
  conjuncts) so ShobdoShakti tile boundaries are deterministic regardless of
  runtime. `tokenizeToTiles()` strips whitespace/punctuation tokens for
  direct use as game tiles.

Supporting functions:

- `normalizeBengali()` - NFC composition (Bengali defines canonical
  decompositions for the two-part vowel signs ো/ৌ, so NFC alone fixes most
  encoding drift) plus stray ZWJ/ZWNJ cleanup (kept only when they
  immediately follow a virama, where they steer conjunct glyph choice).
- `normalizeForSearch()` - the above, plus dropping optional
  nasalization/trailing marks users often omit, for lenient matching.
- `normalizeForDictionary()` - the strict canonical form used as the
  `dictionary_words.normalized_word` dedup key, so two different valid
  encodings of one word never create two rows.
- `isValidBengaliWord()` - structural well-formedness (no orphan vowel
  sign, no dangling virama), not a dictionary lookup.

All of this is exercised by 25 unit tests covering conjunct merging,
NFC-equivalence dedup, orphan-matra/dangling-virama rejection, Bengali
numeral conversion, and grapheme-vs-akshara boundary differences
(`packages/bengali/test/`).

## 4. Game engine design

`packages/game-engine` has zero DB/network dependency - dictionary lookup
is injected as a plain function (`DictionaryLookup = (word) => boolean`),
so the same engine works against the bundled offline word list today and a
real `dictionary_words` table later without any engine change.

- `board.ts` - pure grid operations: placement, in-bounds/occupancy
  checks, `getFormedWords()` (walks outward from each newly placed tile in
  both directions to find the complete word it belongs to - including the
  single-tile-move exception described below), and `getBonusType(row, col,
size)`, an **original** bonus-square layout algorithm (concentric
  "rings" restricted to the board interior - nothing on the outer border,
  and never at a corner or edge-midpoint) so it can't be mistaken for any
  existing word-board game's published premium-square pattern. Verified by
  tests for 90°-rotation symmetry, sparse density (<15% of cells), and zero
  border cells.
- `tileBag.ts` - shuffle + draw, with an injectable RNG for deterministic
  tests.
- `distribution.ts` - `buildDistributionFromWords()` derives tile counts
  and point values directly from a word list's akshara frequency (via
  `tokenizeToTiles`), rather than a hand-tuned letter-frequency table -
  common aksharas get more copies and fewer points, rare ones the reverse.
- `validateMove.ts` - move legality: straight line, no gaps, first move
  covers the center cell, follow-up moves connect to existing tiles, every
  formed word passes the injected dictionary lookup. Returns structured
  `MoveError` objects (`{ code, detail? }`), not hardcoded prose, so the UI
  layer owns all copy/localization - the engine never hardcodes English (or
  any) text.
- `score.ts` - `scoreFormedWord()` applies letter/word bonus multipliers,
  but **only** to cells that were newly placed in _this_ move (tracked via
  a `newlyPlacedKeys` set) - reusing an already-placed tile in a later word
  never re-triggers its bonus, the standard word-board convention.
- `gameState.ts` - the `initGame`/`applyMove` reducer. `applyMove` never
  mutates its input; it returns a new state or the original state plus
  errors.
- `levels.ts` - loads the 1000-level dataset (`src/data/shobdoshakti-levels.json`,
  ~515KB) and exposes `getLevel(n)`, `getAllLevels()`, `getAllTargetWords()`,
  `TOTAL_LEVELS`. Deliberately framework-agnostic (no Next.js/`server-only`
  import here) so it stays reusable outside `apps/web` later (AI opponent,
  multiplayer, mobile, tournaments - see §12);
  `apps/web/src/lib/wordLevels.ts` is the thin `server-only`-guarded
  wrapper that keeps the 515KB file out of any client bundle.

**A real correctness bug found and fixed during this pass:** two of the
1000 levels (14, 163) have single-akshara target words (e.g. "মা"). The
original `getFormedWords()` required 2+ cells to count as a "word," which
would have made those levels permanently unsolvable - real one-akshara
Bengali words exist and a genre rule copied uncritically from other games
doesn't hold here. Fixed narrowly: a move that places exactly one tile
with no neighbor in any direction is now reported as a length-1 word (so
it still goes through normal dictionary validation), while a tile that's
already part of a 2+ letter run in one direction still never spawns a
spurious 1-cell "word" in the perpendicular direction. Covered by tests in
both `packages/game-engine/test/board.test.ts` and `validateMove.test.ts`.

30 unit tests cover word formation at intersections, first-move/connectivity
rules, gap detection, dictionary rejection, bonus-square scoring, level
completion, the word-seeded bag's solvability guarantee, and full
game-state transitions (`packages/game-engine/test/`).

The ShobdoShakti page (`/play/shobdoshakti`, `GameShell.tsx`) is a thin
router between two modes behind `GameModeToggle` that are **genuinely
different mechanics**, not one mechanic with two configs - each owns its
own hook and component tree, sharing only chrome (`GameHeader`,
`GameModeToggle`, `HelpDialog`):

- **Level Mode** (default, `WordJaalGame.tsx` / `useWordJaalGame.ts`) - a
  শব্দজাল ("word-net") letter-finding game, replacing the original
  single-target board-placement Level Mode. Each of 10 levels has 50
  "combinations": a small multiset of bare Bengali letters (raw
  orthographic units - consonants, independent vowels, dependent vowel
  signs shown with a dotted-circle placeholder - not `tokenizeBengali`
  akshara tiles, since this mode is pedagogically about individual letters)
  and a fixed list of words spellable from them. The player taps letters
  into a word builder and submits; `checkWordJaalGuess()`
  (`packages/game-engine/src/wordJaal.ts`) returns one of four outcomes
  (`correct | already_found | not_in_list | empty`), each surfaced as a
  distinct message (see the already-found bug below), scores via
  `WORDJAAL_TILE_SCORES` (rarer letters worth more, plus a full-rack usage
  bonus), and a combination is complete once every one of its words is
  found. `Skip` advances early at a point cost (floored at zero); `Hint`
  reveals a word for zero points. `WordJaalLevelComplete` shows the
  milestone celebration between levels (`journeyStages.ts`, 10 named
  stages); progress (`currentLevel`, `currentCombinationIndex`,
  `highestUnlockedLevel`, `totalScore`) persists client-side in
  `localStorage` (`progressStorage.ts`, key
  `alapon.shobdoshakti.wordjaal-progress.v3`) - no auth in V0.1, so
  progress is per-browser, not per-account.
- **Free Play** (`FreePlayGame.tsx` / `useFreePlayGame.ts`, unchanged from
  the original design) - the open 15x15 board, drawing its tile bag and
  dictionary from the _entire_ 1000-word board-mode dataset, via
  `buildWordSeededBag` (see below - not `buildDistributionFromWords`,
  which turned out to make the mode nearly unplayable).

**A real playability bug found and fixed (user-reported):** the first
version of Free Play built its tile bag with `buildDistributionFromWords`

- a per-token frequency distribution, the same idea Scrabble's letter bag
  uses. That works for an _open_ dictionary with tens of thousands of words,
  where almost any handful of common letters spells _something_. ShobdoShakti's
  dictionary is the same _closed_ 1000-word curated list Level Mode uses, so
  matching a dealt rack against it requires an exact whole-word token
  sequence, not just "some real word." Measured empirically
  (`packages/game-engine/test/wordSeededBag.test.ts`'s regression test): a
  frequency-based rack could spell _any_ of the 1000 words only ~20% of the
  time, before even considering board placement rules - i.e. most dealt
  hands were dead on arrival, exactly matching the user's report of "not
  possible to create any words."

Fixed with `buildWordSeededBag()` (`packages/game-engine/src/wordSeededBag.ts`):
instead of sampling tokens independently by frequency, it samples whole
words (biased toward shorter ones) and keeps each word's tokens grouped
together, shuffling only the _group_ order. Drawing from the front of the
bag - both the initial deal and every refill, since `drawTiles()` needed no
changes - now reliably yields a hand containing at least one complete,
placeable word. Verified at three levels: a unit test asserting >90%
solvability across trials, and an e2e regression test
(`tests/shobdoshakti/game-flow.spec.ts`) that fetches the real word list,
computes which prefix of the actually-dealt rack is a real word, places
it, and asserts the submit succeeds - not a mocked scenario.

**A real race condition found and fixed:** rapidly skipping/advancing
through শব্দজাল combinations while a level fetch is still in-flight could
let that fetch resolve out of order and overwrite newer state with stale
level data. Fixed with a request-generation counter (`requestIdRef` in
`useWordJaalGame.ts`) that every new level request bumps; an in-flight
fetch only applies its result if it's still the most recent request. This
is exactly the kind of bug that only shows up under fast/automated
interaction, not manual clicking - caught by the Playwright suite, not by
hand-testing. (`GameShell` now mounts `WordJaalGame`/`FreePlayGame`
exclusively via a ternary rather than sharing one engine object across
modes, so the original cross-mode variant of this race no longer applies -
each mode's hook is fully unmounted, not just reconfigured, when the other
is active.)

**A real React Strict Mode bug found and fixed:** `useWordJaalGame`'s
`selectLetter` originally called `setAvailableLetters(prev => { ... nested
setCurrentGuessTiles(...) call inside the updater ... })` - a nested
`setState` call inside another state's updater function. React 18 Strict
Mode double-invokes state updaters in dev to surface exactly this class of
bug: the nested call fired twice, duplicating the guessed tile and
producing a duplicate-React-key console error. Fixed by consolidating
`availableLetters` + `currentGuessTiles` into one `PaletteState { available,
guess }` object, with every action (`selectLetter`, `removeFromGuess`,
`backspace`, `clearGuess`, `submitGuess`, `useHelp`) calling `setPalette`
exactly once with an atomically-computed next value. Verified via
Playwright's no-console-errors test.

**Two real UX bugs found and fixed via live browser testing, not just code
review:** (1) the score-panel and the found-word toast disagreed on digit
script - the toast interpolated a raw JS number (`+30`) instead of
`toBengaliDigits()` (`+৩০`), inconsistent with the rest of the
Bengali-first UI. (2) submitting an already-found word and submitting a
word absent from the combination's list both collapsed into the same
generic "not in this list" message, which is actively misleading for an
already-found (definitely-valid) word. Fixed by threading
`checkWordJaalGuess()`'s real outcome (`already_found` vs `not_in_list`)
through to a distinct message for each, rather than a boolean
correct/wrong flag.

Both datasets are large enough that they must never reach client
JavaScript directly: `apps/web/src/lib/wordLevels.ts` and
`wordJaalLevels.ts` are guarded with the `server-only` package and are
only ever imported from Route Handlers - `GET
/api/shobdoshakti/wordjaal/level/:n` (a single শব্দজাল level, fetched by
Level Mode as the player advances) and `GET /api/shobdoshakti/words` (just
the board-mode word strings, for Free Play's tile bag). The client never
downloads more than the level it's currently playing plus the flat word
list.

Persisting `game_sessions` to Postgres is schema-ready but not wired up
yet (see §9) - both modes are fully client-side/offline in V0.1.

The dataset itself started as a hand-authored draft with two derived
fields (`orthographic_length_approx`, `contains_conjunct`) computed by
raw-codepoint counting rather than the real tokenizer - exactly the
anti-pattern this document warns against elsewhere. Both fields were
regenerated from `tokenizeBengali()` directly
(`packages/bengali/scripts/validate-word-data.ts` and
`fix-word-data.ts`, run against the file's current location at
`packages/game-engine/src/data/shobdoshakti-levels.json` - kept as
reusable tools, not one-off scripts, since any future edits to this
dataset should be re-validated the same way). The 1000 words themselves
are unaffected: no duplicates, no structurally invalid Bengali,
`normalized_word` already correct. Every entry is still tagged
`validation_status: candidate_requires_dictionary_crosscheck` and
`license_status: ...provenance pending` - honest self-flagging that this is
draft content, consistent with the `dictionary_words` provenance rule in
§9 (no `UNKNOWN`/unclassified content ships to production).

### শব্দজাল dataset: a severe defect found, and why it stayed a separate dataset

Level Mode's শব্দজাল mechanic and its 10-level/500-combination dataset
(letters + target words per combination) originated from an external
Firebase Studio prototype the user supplied for reference
(`শব্দজাল-(shobdojaal)/`, left untouched on disk - never mutated in place,
per this project's standing rule; the dataset was copied into
`packages/game-engine/src/data/shobdojaal-levels.json` before any editing).
Its React/Next.js scaffolding (Firebase, genkit AI flows, an anonymous-auth
leaderboard) was discarded per this project's existing multiplayer/AI/
accounts exclusions (§11-adjacent) - only the game rule and dataset were
ported, rebuilt against this project's own UI/UX system and engine
layering.

**Validating the source `game-levels.json` before trusting it
(`packages/bengali/scripts/validate-shobdojaal-levels.ts`) found it was
badly broken: 1035 of 2200 (47%) `canForm` words were not actually
spellable from their combination's own `letters` multiset**, plus 9
structurally invalid words, 144 non-NFC-normalized entries, 6 duplicate
combination keys, and 5 combinations with duplicate word entries - i.e.
the shipped `letters` arrays were hand-guessed rather than derived from the
words they were meant to accompany, so roughly half the puzzle would have
been unsolvable by design. Fixed narrowly and non-destructively
(`packages/bengali/scripts/fix-shobdojaal-levels.ts`): for each
combination, `letters` is regenerated as the exact union-max character
multiset actually required by its (deduped, NFC-normalized) `canForm`
words, and the 9 structurally invalid words are dropped rather than
patched. Re-validated to zero errors after the fix; 381 of 500
combinations needed a `letters` correction.

**Merge decision: kept as a separate dataset, not merged into the existing
1000-word `shobdoshakti-levels.json`.** The two serve different game
mechanics with incompatible units - board-mode levels are keyed by a
single target word's _akshara_ tiles (`tokenizeBengali` output, for
placement on a 15x15 grid), while শব্দজাল combinations are keyed by _bare
orthographic letters_ (for a letter-palette word-finding game with no
board at all) and a combination maps to many target words, not one.
Merging would have forced one dataset to fake the other's shape for no
shared benefit; `getWordJaalLevel()`/`getWordJaalCombination()`
(`packages/game-engine/src/wordJaalLevels.ts`) and
`getLevel()`/`getAllLevels()` (`levels.ts`) remain independent loaders over
independent files, mirroring how the two modes are independent hooks with
no shared engine state.

## 5. Bengali calendar and festival calendar

Two related but separately-testable pieces of `packages/bengali`, both
framework-agnostic per this project's "Bengali logic never lives in React
components" rule:

- **`calendar.ts`** - deterministic Gregorian↔Bengali (Bangabda) solar
  calendar conversion (`gregorianToBengali`, `bengaliToGregorian`,
  `formatBengaliDate`). The real-world Bengali civil calendar's exact new
  year date drifts by a day across decades (it's tied to a solar sankranti
  that doesn't reduce to a simple fixed rule), so this module fixes one
  explicit, documented convention for the current era - Poila Boishakh
  (Boishakh 1) always falls on 15 April, matching the West Bengal civil
  calendar for the years this app cares about - rather than pretending to
  panjika-exact astronomical precision. Falgun (month 11) is the one
  variable-length month, absorbing the leap day so every Bengali year's
  total day count matches the actual number of days between consecutive
  15 Aprils. 9 unit tests cover the Boishakh-1/Choitro-30 year boundary,
  Falgun's leap/non-leap lengths, and full round-trip conversion.

  **A real DST bug found and fixed:** the first version computed day
  offsets by dividing a raw millisecond difference by 86,400,000. A local
  calendar day isn't always exactly 24 hours across a DST transition (23
  or 25), so any date range crossing one silently miscounted by a day -
  caught by a round-trip test converting 29 February 2028 and back, which
  landed on 28 February instead. Fixed by routing all day-counting and
  day-adding through `Date.UTC()` (which has no DST), never raw local
  millisecond arithmetic - the same fix was needed in `festivals.ts`'s
  `daysUntil`/`getFestivalStatus`, which had the identical bug.

- **`festivals.ts`** + **`data/festivals.ts`** - one year of major Bengali
  festivals (Durga Puja through the next Poila Boishakh and beyond, 15
  entries covering autumn 2026 to autumn 2027) with bilingual names/
  descriptions, and query functions (`getAllFestivals`,
  `getUpcomingFestivals`, `getNextFestival`, `getFestivalStatus`,
  `daysUntil`). Unlike the solar calendar above, most festival dates
  follow the lunisolar Hindu Panchang (tithi-based) and genuinely cannot
  be derived algorithmically - they were sourced from published
  Panchang/Panjika references for these specific years and are tagged
  `lunisolar: true` in the data, with a disclaimer surfaced on the
  calendar page itself ("dates can vary by a day depending on the
  panchang/panjika source") - the same honest-self-flagging-of-
  provenance pattern used for `shobdoshakti-levels.json`'s
  `validation_status` field. Durga Puja is modelled as one multi-day
  `Festival` spanning Mahalaya through Bijoya Dashami (with a `days` array
  for the per-day Shashthi..Dashami schedule) rather than as separate
  entries, since Mahalaya _is_ traditionally when Durga Puja's Devi Paksha
  begins - a design choice validated by a real bug caught during manual
  testing (below).

  **A real UX bug found and fixed:** the first version kept Mahalaya as a
  separate, standalone festival entry a week before Durga Puja. Since the
  homepage spotlight picks whichever festival is _nearest_,
  `getUpcomingFestivals()` returned Mahalaya - not Durga Puja - as the
  "glimpse" during the week between them, defeating the entire point of
  the feature (the user had explicitly asked for a Durga Puja glimpse
  since it was coming up). Caught by manually loading the homepage rather
  than trusting the unit tests alone - the query logic was correct, the
  _data model_ was wrong. Fixed by folding Mahalaya into the Durga Puja
  entry as its first `days` item; `getFestivalStatus`/`daysUntil` now
  naturally treat "17 days to Mahalaya" as "17 days to Durga Puja," which
  is also how Bengali media conventionally frames the countdown.

**UI**: `apps/web/src/components/calendar/` - `BengaliDateCard` (today's
Bengali + Gregorian date), `FestivalSpotlight` (the hero "glimpse" card,
with Durga-Puja-specific copy and its day-by-day schedule strip when a
festival has one), `FestivalListItem` (a chronological list row), and two
composition points: `HomeCalendarWidget` (the homepage strip - today's
date plus the next festival's spotlight) and `CalendarPageContent` (the
full `/calendar` page - today's date, the spotlight, the month-grid
calendar below, then every remaining upcoming festival for the year).
Both the homepage and `/calendar` are otherwise statically prerenderable
pages; `useToday()` (`components/calendar/useToday.ts`) deliberately
computes `new Date()` only after client-side mount (returning `null`, and
a skeleton, during the SSR pass) rather than in a Server Component, so
"today" is evaluated fresh in the visitor's browser on every load instead
of getting frozen at the last build time - the same pitfall `next dev`'s
Fast Refresh hides but a real static export would expose.

**Month-grid calendar** (`BengaliMonthCalendar.tsx`) - a traditional
"normal" wall-calendar layout, added alongside the festival list: a 7-
column grid for one Bengali month at a time, Bengali day number leading
(large) with the Gregorian date secondary (small) underneath, today's cell
highlighted, and any festival day marked with its emoji. Built on three
small additions to `calendar.ts` - `bengaliMonthLength()` (exported
version of the internal month-length lookup, so the UI doesn't
re-implement Falgun's leap logic), `bengaliMonthStartWeekday()` (which
Gregorian weekday a Bengali month's 1st falls on, for the grid's leading
blank cells), and `addBengaliMonths()` (wraps the year at the
Choitro/Boishakh boundary for the prev/next-month buttons) - all covered
by unit tests, including the year-wrap cases. Read-only but marked up with
proper calendar-grid ARIA (`role="grid"`/`"gridcell"`, `aria-current="date"`
on today, a combined Bengali-date + festival-name `aria-label` per cell)
rather than plain `<div>`s with no semantics, mirroring the same
"never color/position alone" accessibility standard `BoardCell.tsx` set
for the game board.

## 6. Welcome banner: rooting the site in Bengali culture

A once-per-visitor modal (`apps/web/src/components/WelcomeBanner.tsx`),
mounted in `[locale]/layout.tsx` so it's the first thing anyone sees
regardless of which page they land on - not scoped to the homepage, since
a shared link can land a first-time visitor anywhere. Deliberately not
another feature pitch: it leads with the brand's own "আমাদের শিকড়,
সবসময় আমাদের সাথে" (Our roots, always with us) tagline, a short
warm paragraph naming the cultural pillars the whole product is built
on (ভাষা ও সাহিত্য, উৎসব, সংস্কৃতি, আড্ডা), and a single dismiss CTA -
no feature tour, no signup ask, consistent with this project's "core
experience stays free, no accounts in V0.1" stance. Dismissal persists via
`localStorage` (`alapon.welcome-banner-dismissed.v1`, same try/catch-
guarded read/write pattern as `progressStorage.ts`'s onboarding flag), and
the dialog itself reuses `HelpDialog.tsx`'s established modal shape
(`role="dialog"`, `aria-modal`, initial focus, Escape-to-close,
`prefers-reduced-motion`-aware) rather than inventing a second modal
pattern.

**A real test-suite bug this surfaced:** making the banner site-wide
(mounted in the shared layout, not a page) meant every existing Playwright
test's very first navigation now hit a full-viewport modal overlay with no
`pointer-events: none`, which silently intercepts clicks on anything
behind it - e.g. the language switcher and nav-link tests, which click
immediately after `page.goto()`. Every test file now goes through a
`gotoWithoutWelcomeBanner()` / `gotoGame()` helper (`tests/e2e/helpers.ts`,
`tests/shobdoshakti/helpers.ts`) that pre-seeds the dismissal flag via
`page.addInitScript()` before navigating, the same pattern already used
for ShobdoShakti's onboarding dialog - and a dedicated
`welcome-banner.spec.ts` tests the undismissed first-visit path on its
own, deliberately bypassing that helper.

## 7. Quiz: the daily quiz and the level quiz

`packages/game-engine/src/quiz.ts` + `data/quiz-questions.ts`, surfaced at
`/quiz` (`apps/web/src/components/quiz/`), on the `/play` hub, and as a
card in the homepage's "what's here today" grid. 21 bilingual
multiple-choice questions (history, culture, literature, festival,
language, geography), each with a short explanation shown after answering,
restricted to well-established, uncontroversial facts (deliberately no
contested-origin claims such as which region "invented" a sweet).

"Daily" is a pure function of the date, not server state:
`getDailyQuiz(date)` shuffles the bank with a mulberry32 PRNG seeded from
days-since-epoch and takes 5, so every visitor sees the same quiz on a
given day with no database or API route (the bank is a few KB, unlike the
515KB word datasets that need the `server-only` route treatment).
`useDailyQuiz` computes "today" only after client mount (same reason as
`useToday`) and persists per-day progress in `localStorage`
(`alapon.quiz.progress.v1`, date-stamped so yesterday's record is
ignored), so a mid-quiz reload resumes and a finished quiz shows its
result.

**A real integrity bug found and fixed:** the first version served
options in authoring order, and 18 of 21 questions had the correct answer
written first - so always clicking option 1 scored ~85%. Caught when a
throwaway script that always clicked the first option scored 5/5, not by
the unit tests (which read `correctIndex` dynamically and so passed). Fixed
in the engine, not by hand-editing 18 questions: `withShuffledOptions()`
reorders each served question's options with a PRNG seeded from
(day XOR hash of question id) and remaps `correctIndex`, keeping the data
readable and the served order deterministic per day. Locked in by unit
tests (same options after reorder, `correctIndex` still points at the
right text, positions not clustered across 30 days) and an e2e test that
reads the live correct-answer position across a full quiz.

**A real test-suite flake, hardened:** the welcome banner's Escape-to-close
test failed reproducibly in the full suite while passing alone, and
bisection showed it depended on which other specs had run before it.
`WelcomeBanner` now uses a stable `useCallback` close handler and a
window-level capture-phase `keydown` listener instead of a document-level
bubble listener re-created per render.

### Level quiz: 1,000+ questions, ten levels

`/quiz` is now a hub: the daily quiz (moved to `/quiz/daily`) plus a
progression of **10 levels x 10 sets** (`/quiz/level/N`,
`/quiz/level/N/S`), 1,094 bilingual questions mixing history, geography,
culture, literature, religion, festivals, language, arts and
personalities of Bengal and Bengalis. Levels run Novice -> Grand Master
(নবীন, পথিক, অনুসন্ধানী, পাঠক, জ্ঞানী, বিদ্বান, পণ্ডিত, মনীষী, বিশারদ,
মহামনীষী) with rising difficulty; every level blends all categories. A
set is passed at 70% (rounded up) and passing unlocks the next set, the
last set of a level unlocking the next level - the same sequential-unlock
shape as the শব্দজাল levels.

Structure and boundaries (all covered by tests):

- **Data**: `packages/game-engine/src/data/quiz-bank/l01a.ts ... l10.ts`,
  one compact row per question (`[category, questionBn, questionEn,
correct, wrong, wrong, wrong]`, correct answer written first; bare
  strings for numbers/years, digits localised to Bengali automatically).
  The directory is in `.prettierignore` - reformatting would spread 1,000+
  one-line rows over thousands of lines.
- **Engine**: `quizLevels.ts` expands rows, deterministically mixes each
  level (so sets blend categories instead of clustering by authoring
  order), splits it into 10 sets of 10-12 questions (every question used
  exactly once), and reshuffles each set's options per question. Pure
  progression rules (`quizProgress.ts`: pass threshold, unlock chain,
  next-set resume, best-score records) are a separate data-free module so
  client code can import them without pulling the bank.
- **Bundle boundary**: like the word datasets, the bank is server-only.
  `apps/web/src/lib/quizBank.ts` is `server-only` and only the route
  handler `GET /api/quiz/set/[level]/[set]` imports it, so a visitor
  downloads one ~10-question set at a time. `game-engine` is marked
  `"sideEffects": false` so tree-shaking keeps the bank out of client
  chunks - verified by build output (the quiz pages ship 119-134 kB first
  load, unchanged in order of magnitude from before the bank existed).
- **Progress**: best score per set in `localStorage`
  (`alapon.quiz.levels.v1`, per browser, no accounts in V0.1), re-read
  before every write so two open tabs can't clobber each other. A locked
  set requested by URL shows a locked page rather than the questions.
- **Categories/copy**: three new categories (religion, arts &
  entertainment, personalities); `explanation*` became optional on
  `QuizQuestion` because the large bank ships without per-question
  explanations - a wrong answer instead reveals the correct one.

**Content integrity, and what a test can't catch.** The integrity suite
(`quizLevels.test.ts`) enforces >=1,000 questions and >=100 per level,
both languages present, exactly four distinct options in each language,
unique ids and no duplicate question text, all nine categories present and

> =6 mixed inside every level, no leftover authoring artifacts
> (ellipses, "X নয়, Y" fragments), sets that partition each level exactly,
> and that options really are reshuffled with `correctIndex` remapped. But
> tests cannot verify _truth_. The first draft of levels 5-8 contained
> several garbled or nonsensical stems and weak "not X, Y" distractors
> that only a human read-through caught; each was rewritten or replaced by
> a scripted cleanup, and then every question in levels 6-10 was re-read
> against known facts, which found and fixed one more (the Daily Ittefaq
> was _edited_, not founded, by Manik Mia). Treat the bank as
> **editor-reviewed, not authoritative**: lunar/contested facts were
> avoided, but a subject-matter reviewer should sign off before public
> launch, consistent with this project's provenance rule for content.

## 8. i18n and design system

`next-intl` with `localePrefix: "always"` and `localeDetection: false` -
Alapon is Bengali-first per the decision log, so `/` always resolves to
`/bn` rather than guessing from `Accept-Language`; users switch explicitly
via the header's `LanguageSwitcher`. All UI copy lives in
`apps/web/src/messages/{bn,en}.json`, including ShobdoShakti's move-error
strings (keyed by the engine's error codes).

**Palette and typography** follow a "Modern Bengal" direction (NYT
Games + modern mobile word games + Bengali editorial design), not festive-
decorative and explicitly not a Scrabble reskin: warm ivory backgrounds
(`cream`, exact hex `#FFF9F0`/`#FFFCF7`/`#F7EEDC`/`#E7DDCB` per the
ShobdoShakti visual spec), Bengal red (`sindoor`, `#C62828`/`#7A1F1F`) as
the primary interaction color, muted antique gold (`marigold`, `#C89B3C`)
for secondary actions and score/celebratory accents, `alpona` (terracotta)
kept only for the brand wordmark, and `shapla` (green) reserved for
success states so it never collides with red/gold. All defined once in
`packages/config/tailwind-tokens.js` and consumed by both
`apps/web/tailwind.config.ts` and `packages/ui`. Headings use **Noto Serif
Bengali** (`font-bengaliDisplay`) for an editorial, premium feel rather
than a playful display face; body copy uses Noto Sans Bengali; both are
loaded via `next/font/google` in `apps/web/src/lib/fonts.ts` and wired as
CSS variables on `<html>` so Tailwind's `font-bengali`/`font-bengaliDisplay`
utilities resolve to real loaded fonts rather than system defaults.

`packages/ui` holds the design system: `Button`, `Card`, `Badge` (now
`default | festival | gold | muted` tones), `Container`, `SectionHeading`,
`LanguageSwitcher`, `PlaceholderPanel` (used by the Discover/Theke Adda
"coming soon" pages so they're real, navigable, on-brand pages rather than
404s), and `AlponaDivider` - a small tiling SVG wave-and-dot line motif
(pure `currentColor` line art, not a literal alpona reproduction) used as a
section divider in the hero, footer, and placeholder pages for a cultural
touch without being kitschy.

**Mobile-first specifics worth knowing:** all interactive elements target
a 44px (`min-h-11`) minimum tap height; the header is a single row on
`sm:` and up but stacks into two rows on narrow phones (logo+language row,
then a horizontally-scrollable nav row) rather than truncating or wrapping
nav text mid-word - an earlier version let flex-shrink wrap link text
inside the pills at 375px width, since fixed by giving every nav link
`shrink-0 whitespace-nowrap` and moving the language switcher to its own
row below `sm:`.

## 9. Database foundation

`database/schema/schema.prisma`, scoped to what this pass needs:

- `users` - minimal fields only (no location, no contacts).
- `content_sources` / `dictionary_words` - provenance-first: every word
  traces to a source with an explicit `LicenseStatus`
  (`PUBLIC_DOMAIN | OPEN_LICENSE | CREATIVE_COMMONS | COMMERCIAL_LICENSE |
USER_SUBMITTED | INTERNAL | UNKNOWN`). `normalized_word` is unique and is
  the `@alapon/bengali` `normalizeForDictionary()` output.
- `games` / `game_sessions` - generic enough for any future game, not just
  ShobdoShakti; `metadata` is a JSON escape hatch for per-game detail.

No `posts`, `comments`, `reports`, `businesses`, or `payments` tables yet -
those are Theke Adda/marketplace concerns, explicitly out of scope here.
`database/seeds/dictionary.seed.ts` seeds its own small internal word list
(distinct from `packages/game-engine/src/data/shobdoshakti-levels.json`,
which the web app serves directly from a static file via `@alapon/game-engine`,
not the database, in V0.1), tagged `INTERNAL` (development seed, not a
licensed import).

## 10b. Accounts, leaderboard and Theke Adda (Supabase)

- **Backend:** Supabase Postgres + Auth, accessed from the browser with the publishable key; **row-level security** in `database/migrations/0001-0003` is the real access control (private profiles by default, users cannot change their own role/suspension, adult-only posting, blocks hide content, moderators have narrow update rights). Run migrations in order in the SQL editor.
- **Accounts:** `AuthProvider` (context), `/login` (password or emailed link), `/account` (display name, username, public-leaderboard opt-in, self-declared 18+). Missing env vars degrade gracefully (site works, account features hidden).
- **Scores:** saved after daily/level quizzes (best score kept). They are client-submitted, so the leaderboard is casual, not tamper-proof; a prize leaderboard needs server-side validation.
- **Theke Adda:** nine sections, posts, comments, likes, report, block, and a moderator queue at `/moderation` (remove content, dismiss, suspend 7 days; actions go to `moderation_audit_log` through a moderator-only function). Public reads use `post_feed`/`comment_feed` views that show author display names and re-apply visibility rules. Rate limits: 5 posts and 30 comments per author per hour. No direct messaging.
- **Deliberately not yet built:** AI risk classification, automated spam detection, appeals, a formal copyright-report page and admin user management. Content is published immediately and reviewed after reports (post-moderation).

## 10c. Learn Bengali from scratch

- **Curriculum** (`packages/game-engine/src/data/learn-curriculum.ts`): six units, 28 lessons - vowels, consonants (by varga), vowel signs, numbers, everyday vocabulary (8 topics) and conjuncts. Pronunciation romanisations are unique within a unit so they can serve as unambiguous quiz answers (tested).
- **Exercise engine** (`learn.ts`): pure and seeded. A lesson becomes introduction cards, then multiple-choice (both directions), "which letter does this word start with / which conjunct does it contain", a matching round and, for vocabulary, word-building from `tokenizeToTiles` tiles (with a hint that never gives credit). Wrong answers are requeued once for practice and not scored again. Options never repeat a label.
- **Progress** (`learnProgress.ts` + `lib/learnProgress.ts`): stars from first-try accuracy (never lowered), XP, and a daily streak, stored in localStorage (`alapon.learn.progress.v1`). Nothing is locked - learners can jump in anywhere, and the path highlights the next lesson.
- **UI** (`components/learn`): `/learn` path, `/learn/[lessonId]` player, `/learn/alphabet` reference chart. Exercises are generated after mount (time-seeded shuffle) to avoid a server/client hydration mismatch.
- **Pronunciation audio** uses the browser's Bengali text-to-speech voice when the device has one, and hides the speaker buttons otherwise; recorded native-speaker audio is the recommended upgrade.
- **Content review:** romanisations, hints and examples were authored by hand and should be reviewed by a fluent Bengali speaker/teacher before launch.

## 10d. Share cards and friend challenges

- **Share card:** finishing the daily quiz builds a Wordle-style, spoiler-free message (`shareGrid`: one green/red square per question, plus score and date) and a challenge link, sent through the native share sheet or copied. Pure helpers live in `packages/game-engine/src/quizShare.ts`.
- **Challenge link:** `/quiz/challenge?d=<date>&s=<score>&n=<name>`. The daily quiz is a deterministic function of the date, so any past day can be replayed and compared with the friend's score - no server state. Link parameters are untrusted, so `parseChallenge` validates them (real date from 2026-01-01 to tomorrow, score 0-5, name stripped of markup/control characters and capped at 24 characters). Nothing from a challenge is stored.
- **Link previews:** `/api/og` renders a 1200x630 PNG (edge runtime, `next/og`) and the challenge page sets Open Graph metadata. Satori mis-orders Bengali vowel signs (e.g. "প্রিয়া", "চ্যালেঞ্জ" come out garbled), so the image uses only the brand word, Bengali digits and English text and omits the challenger's name. `NEXT_PUBLIC_SITE_URL` must be set in production so preview URLs are absolute.

## 10e. Loading feedback

- **`NavigationProgress`** (mounted in the locale layout): a thin sindoor/marigold bar at the top that starts the instant an in-app link is clicked (same-origin, plain left-click, different URL) or `announceNavigationStart()` is called (language switch), eases towards 90%, and completes when the pathname changes. ## 11. Deliberately deferred

- Auth is schema-ready (`User.authProviderId`) but no provider is wired up;
  ShobdoShakti plays fully anonymously/offline in V0.1. Level Mode progress
  (`currentLevel`/`currentCombinationIndex`/`highestUnlockedLevel`/
  `totalScore`) lives in `localStorage`, per-browser - it is not tied to an
  account and won't survive clearing site data or switching devices until
  auth + `game_sessions` persistence land.
- `game_sessions` persistence, leaderboards, and Redis are not wired up -
  the schema exists, the write path doesn't yet.
- Payload CMS, Redis, R2/S3, Sentry, PostHog: not introduced - nothing in
  this pass needs them yet, and adding them now would be exactly the kind
  of premature infrastructure the product brief asked to avoid.
- ShobdoShakti's own future features (মহাশব্দ full-rack bonus beyond the
  existing `FULL_RACK_BONUS`, শব্দবাজি rare-word bonus, বাংলা শক্তি
  special bonus, দৈনিক শব্দ daily challenge) are intentionally not built -
  `GameMode` already includes `"daily"` in its type union (unused) as a
  placeholder for the last one, and the deterministic, side-effect-free
  scoring/validation engine has no assumptions baked in that would block
  adding the rest later.

## 12. Why this stays extensible (AI, multiplayer, tournaments, leaderboards)

None of these are built, but the layering was chosen so adding them later
doesn't require reworking the core: `packages/bengali` and
`packages/game-engine` have zero React/Next.js/DB dependency, so an AI
opponent or a server-authoritative multiplayer mode can import the exact
same `validateMove`/`scoreMove`/`applyMove` functions the client uses
today - there is no "client version of the rules" to keep in sync with a
server version. `levels.ts` living in the engine (not the web app) means a
future mobile app or a tournament service can read the same level
dataset without depending on Next.js. `game_sessions` already has a
`metadata: Json` column sized for whatever a leaderboard or daily-challenge
feature needs to record, without a schema migration to add the first one.
